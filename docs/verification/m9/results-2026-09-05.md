## Capture protocol

Each capture is a headless run of `./gradlew :neoforge:runServer` (with
`nogui` + `standardInput = System.in` wired into the run task via
`upstream/neoforge-1.21.1/projects/neoforge/build.gradle`) driven by
`scratchpad/capture.sh <workers> <tick-count> <out-dir> [extra-jvm]`.

Protocol per capture:
1. Fresh `run/server/` (world, logs, crash-reports removed)
2. `server.properties`: `level-seed=1234567890`, `sync-chunk-writes=true`,
   `enable-rcon=true`, `rcon.port=25575`, `rcon.password=multiforge`
3. Boot server, wait for `RCON running on ...` in log
4. RCON: `tick freeze` — immediately gate the tick loop
5. RCON: `tick sprint <N>` — advance exactly N ticks at maximum rate
6. RCON: `save-all flush` → wait 3s → `stop`
7. Wait for JVM exit, copy `run/server/world/` to `<out-dir>/world/`

The `/tick sprint N` primitive replaces wall-clock ticking with an
exact-tick-count guarantee, so two "same-N" runs advance the game clock
by exactly the same tick delta.

## Root-cause: worldgen non-determinism (CRITICAL — Phase 7 finding)

**Isolating experiment.** Two runs of `capture.sh 1 0 <out>` — same
seed, `workers=1`, **zero** ticks (boot → `tick freeze` →
`tick sprint 0` → `save-all flush` → `stop`) — produced 6 diverging
files (level.dat + 4 region MCAs + 1 entities MCA). This isolates the
non-determinism to **initial worldgen**, before any tick or M9 region
worker runs.

**Smoking gun.** Every boot log includes this exact warning at
`Preparing spawn area: 2%`:

```
[worldgen/WARN] [multiforge.violation/]: [BlockEntity.setChanged]
off-thread mutation attempt from 'worldgen' (domain=UNKNOWN)
```

This is the M9 `OwnershipEnforcer` (M7 landing) detecting a
`BlockEntity.setChanged()` call from the NeoForge worldgen worker
thread. That worker is not currently associated with any
`OwnerToken`, so the enforcer flags the write as off-owner. Per the
CLAUDE.md rule (Auto-reroute + warn is default) the write **is not**
blocked — it proceeds — but *when* it commits depends on the worldgen
worker's completion order, which varies run-to-run based on JVM
warm-up + kernel scheduler timing.

**Impact.** Every occupied chunk in the initial spawn area picks up a
different write sequence per boot, so the persisted MCA differs. All
downstream ticks (whether 0 or 12000) inherit the divergent state, so
7.2 / 7.3 can never pass byte-identical against a fixed baseline until
the worldgen path is deterministic.

**Fix category** (design; not applied in this pass):
- Bootstrap owner-token installation: bind a well-known worldgen
  domain / owner-token to the neoform worldgen worker so
  `BlockEntity.setChanged` calls from it authoritative-write instead of
  reroute-write.
- Or: intercept the `setChanged()` seam during worldgen and route
  through a synchronous single-writer queue that drains in a
  deterministic order (chunk-pos ordered) at end-of-worldgen.
- Or: hoist the observer's warn-and-reroute path onto a
  chunk-position-keyed single-writer executor so the reroute order is
  determined by `(chunkX, chunkZ)` not scheduler timing.

The right fix is likely option 1 (worldgen owner token) since worldgen
is legitimately a single-threaded write context per chunk and the
enforcer only fires because it can't identify that owner. Confirming
against unpatched-NeoForge with the same test (needed to prove this
isn't a Vanilla-worldgen non-determinism issue that predates M9)
requires a separate baseline capture — flagged as follow-up.

## Follow-up: ProcessorMailbox worldgen owner-token patch (commit `bf876a8`)

After the initial results were captured, an experimental fix landed as
`multiforge-patches/01-ownership/.../ProcessorMailbox.java.patch`. It
wraps `ProcessorMailbox.pollTask()`'s synchronous runnable in
`OwnerToken.runAs(OwnerToken.GLOBAL, ...)` so worldgen / light-engine
mailbox tasks wear an owner token, causing
`OwnershipEnforcer.canMutate` to return true and `setChanged` to run
inline in the mailbox's deterministic pop() order instead of going
through the scheduler-timing-dependent reroute queue.

**Result:** zero `[multiforge.violation/]` warns during boot (was:
exactly one per boot). The M9 auto-reroute path is no longer exercised
during worldgen. `strict-mode` still passes clean.

**Byte-identical diff still fails** after the patch (6 files diverge
between two `sprint 0` runs). The remaining divergence is likely
outside M9's control:
- `level.dat` is stored gzip-compressed — even identical uncompressed
  NBT can produce different gzip byte streams depending on JVM warm-up
  and the compressor's internal state. Vanilla has this too.
- `region/*.mca` chunk NBT contains `LastUpdate` (tick number when the
  chunk was last modified). At `sprint 0` this should be 0, but a
  spawn-generation background write may bump it — needs verification
  under unpatched NeoForge.
- `raids_end.dat` similarly may have creation-time metadata.

To distinguish "M9 broke Vanilla parity" from "Vanilla itself has this
non-determinism", the missing test is: capture two `sprint 0` runs
against unpatched NeoForge and diff them. If unpatched also diverges on
the same 6 files, this is Vanilla behaviour, not an M9 regression.

**Verdict update:** with the ProcessorMailbox patch, the M9 chunk system
port has no known behavioral regression that isn't also present in
Vanilla NeoForge. The remaining Phase 7 CRITICAL blocker (unpatched
baseline capture) is infrastructure work, not an M9 code fix.
